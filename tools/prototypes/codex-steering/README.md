# Изолированный прототип управления ходом Codex

Этот каталог — проверочный стенд, не подключённый к runtime бота или интерфейсу
Telegram. Он не меняет штатный Claude, авторизации, сессии, очередь и `/stop`.
Новый пользовательский сценарий ещё не установлен и не готов к выпуску.

До прототипа основной Codex-адаптер использует `codex exec --json` и закрывает
stdin после запроса: [адаптер](../../../overlay/bot/ext/adapters/codex.mjs),
[запуск процесса](../../../.msb/bot/src/agent/claude.mjs). Общий
[inbox](../../../.msb/bot/src/telegram/inbox.mjs) выполняет один ход, объединяет
соседние ожидающие тексты, а `/stop` очищает ожидание и отменяет ход. Старый
эталон для FIFO и `/stop`: master `00f081f2220d0e6d3a186e8e1bb447b57acd6ebf`,
readable blob `73aa9e7e850bad7ac1ea8a8091d086ecbfd47a11`: `git show <blob>`;
строки 105472–105482, 110140–110151 и 118208–118249. Управление текущим Codex
через `turn/steer` — отдельно запрошенное расширение, не утверждение о старом ядре.

## Состав и границы

- [queue.mjs](queue.mjs) моделирует один изолированный scope: обычное сообщение
  остаётся FIFO, выбранное резервируется и передаётся в активный turn. Это
  экспериментальная очередь, а не вторая очередь runtime. Она не реализует
  склейку, вложения, цитаты, формы, Telegram callback и собственно bot `/stop`.
  Проверка строкового scope в стенде не заменяет Telegram owner guard.
- [session.mjs](session.mjs) запускает собственный app-server, создаёт только
  новый `ephemeral` thread и адресует `turn/steer` конкретному `turnId`.
  [rpc.mjs](rpc.mjs) отделяет ответы от запросов сервера и не подтверждает их.
- [queue.test.mjs](queue.test.mjs) и [rpc-session.test.mjs](rpc-session.test.mjs)
  проверяют FIFO, одиночную передачу, запрет чужого scope, повтор нажатия,
  сохранение очереди при явно доказанном отказе, неизвестный результат RPC,
  `/stop`, гонки и ограниченное завершение процесса.
- [native-loopback.mjs](native-loopback.mjs) использует настоящий Codex 0.166.0
  внутри одноразового Linux-контейнера с `--network none`, фиктивную модель на
  его loopback и полностью синтетические профиль и авторизацию. Проверяет, что
  поправка фактически появляется во входе модели в том же ходе, ожидающее
  сообщение начинает новый ход, а прерванная очередь не запускается.
- [native-live.mjs](native-live.mjs) требует явно подготовленный отдельный профиль
  в личном каталоге `/tmp/jarvis-steer-live-*`, отдельные пустые HOME/workspace
  и ключ `--allow-live-model`. Он использует реальную модель и расходует лимит
  аккаунта. В настройках отключены shell, MCP-серверы, браузерные инструменты,
  плагины и другие явно перечисленные возможности; тест не вызывал инструменты. Скрипт
  сам не читает и не копирует личную авторизацию; происхождение предоставленных
  оператором учётных данных проверкой каталога не доказывается. Не использовать
  существующий профиль или реальные пользовательские сессии.
- [native-cleanup-loopback.mjs](native-cleanup-loopback.mjs) в отдельном PID
  namespace проверяет случай, когда процесс-лидер завершился, а потомок с
  закрытыми pipes продолжает жить в его группе.

Для неопределённого результата старта или interrupt очередь блокируется, а
тестовая сессия закрывается; после потерянного ответа на steer автоматического
повтора нет. Generic RPC error сам по себе не считается доказанным отказом до
принятия. Таймаут завершения возвращает неизвестное состояние и сообщает,
если закрытие процесса не удалось подтвердить. Наблюдение за группой процесса
не обнаруживает потомка, самостоятельно перешедшего в другую группу: для
полной гарантии уборки требуется отдельная системная изоляция. Персистентная
очередь, восстановление после перезапуска и согласование неизвестного результата
здесь не реализованы.

## Проверки 17.11.2026

- 23 модульные проверки управления очередью, RPC и завершения процесса — PASS
  на macOS и на Node 22 в изолированном Linux.
- 39 существующих проверок `inbox`, Telegram lifecycle, Claude abort/partial —
  PASS с фиктивными Telegram и CLI. Реальный Claude не запускался.
- 19 проверок переключения Claude ↔ Codex и сохранения сессий — PASS на
  фиктивных auth и CLI; реальное переключение не выполнялось.
- Официальный Codex `0.166.0` Linux arm64 с контрольной суммой npm — PASS в
  контейнере без сети: четыре синтетических model request, один активный turn
  с поправкой, отдельный queued turn, interrupt и очистка очереди. Это та же
  версия CLI, но не архитектура JAR1; реальную модель этот тест не проверяет.
- Локальный Codex `0.169.0-alpha.11.1` macOS arm64, реальная модель и новый
  ephemeral thread — PASS: она ответила с поправкой в первом ходе, приняла
  следующее сообщение отдельным ходом, затем interrupt остановил ещё один ход
  и очередь очистилась. Использован отдельный временный профиль; исходные файлы
  auth/config совпали по отпечаткам до/после. Временный профиль удалён.
- Реальный процесс с дочерним процессом в том же process group обнаружен в
  отдельном контейнере; неизвестная уборка не выдаётся за успешную.

Код JAR1, его профиль, текущий диалог и интерфейс Telegram не затрагивались.
Тест настоящей модели относится к локальной alpha-версии, а проверка 0.166 —
к синтетической модели; совместимость полного product-пути и реальная модель
через 0.166 остаются отдельной проверкой.

```sh
node --test --test-concurrency=1 \
  tools/prototypes/codex-steering/queue.test.mjs \
  tools/prototypes/codex-steering/rpc-session.test.mjs
```

Для native loopback использовать проверенный vendor-каталог официального
`@openai/codex@0.166.0-linux-arm64` как `JARVIS_CODEX_VENDOR`; исходник и
vendor монтируются только для чтения, временные файлы — внутри контейнера:

```sh
docker run --rm --init --network none --read-only --tmpfs /tmp:exec,mode=1777 \
  --mount type=bind,src="$PWD",dst=/repo,readonly \
  --mount type=bind,src="$JARVIS_CODEX_VENDOR",dst=/native,readonly \
  -w /repo msb-local-checks:node22-forms \
  node tools/prototypes/codex-steering/native-loopback.mjs /native/bin/codex
```

Следующий этап при отдельном поручении — интеграция с существующим `inbox` и
Telegram: атомарный выбор именно ожидающего сообщения, сохранение его quote и
контекста, обратная связь после подтверждения, проверка смены сессии и провайдера,
голоса, повторных нажатий и `/stop`. Нельзя переносить стендовую очередь в
runtime как параллельную реализацию штатного inbox.
