JAR1 — выборочный выпуск исправлений бэклога, 16.11.2026

База: принятый на JAR1 c56f30bf97dea2fe159a7f4e07537388d619a7c9.
Кандидат — отдельный потомок этой базы; в приложении выбраны только 30 файлов
монитора, паузы расходов, фоновых задач и обработки /stop из рабочей ветки.
Настройки, авторизации, сессии и системный engine в payload не входят. Новый
код и визуальные сценарии OpenClaw не разрабатываются и не проверяются.

build.py экспортирует исходник, 25 замен и пять добавлений из одного Git
commit и проверяет неизменность остальных runtime-путей. Два старых README,
один ext README и package.json отражают уже принятые исключения сервера.
verify.py проверяет исходник и hash каждого payload, использует выбранные
общие тесты и синтетический HOME. Фоновые тесты запускают подменённый соседний
диспетчер, а смешанные файлы отбирают сценарии положительными именами.
На сервере запускать от client в новых PID/network/mount namespaces: loopback
доступен, внешней сети нет, /run закрыт отдельным tmpfs. Исходный OpenClaw и
личные данные в тестах не используются. Исключённые проверки, количество
тестов и ограничения фиксируются в acceptance; UID-тесты отдельно в Linux.

Перед записью deploy.py проверяет базовый инвентарь, результаты полного
допустимого прогона, идентичность runtime, отсутствие активной работы и
выключенные системные триггеры. После остановки бота он создаёт отдельную
закрытую копию профиля и native Codex-сессий в BACKUP/profile: SQLite через
backup API, не через копирование незакрытого WAL; сеанс сверяется по state,
индексу и метаданным rollout. Копия проверяется по hashes и SQLite quick_check;
COMPLETE.json появляется только после проверки и fsync. Копия содержит
секреты и личную историю: каталог root 0700, файлы 0600, не экспортировать и
не включать в Git. Она является структурной копией на том же диске, не
гарантией сохранности при отказе сервера или работоспособности истёкшей auth.
Исправление не восстанавливает содержимое профиля автоматически.

Далее оператор атомарно заменяет только разрешённый код, проверяет защитные
снимки до/после перезапуска и хранит отдельную закрытую кодовую точку отката.
При отказе запускается проверенный rollback, guard.pending не снимается при
неясном состоянии. Ручной откат выполняется только проверенным оператором:
python3 -I -B STAGE/deploy.py --stage STAGE --backup BACKUP \
  --manifest-sha MANIFEST_SHA --report-sha REPORT_SHA --rollback
Он откатывает только код и не возвращает историю/настройки поверх новых данных.
Ручное восстановление профиля требует отдельно проверить актуальность и не
перезаписывать новые сессии; тест реконструкции выполняется на синтетических
данных, а не на живом аккаунте.
