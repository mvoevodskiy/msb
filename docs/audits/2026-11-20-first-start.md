## Проверенная последовательность

Новый [codex-first-start.test.mjs](../../.msb/bot/tests/codex-first-start.test.mjs)
начинается с поставляемого seed и отсутствующих `state.json`, хранилища
провайдеров и файла нативной авторизации. Выбор Codex и сессия заранее
не подставляются. Используются настоящие `prepare()` обвязки, восстановление
проекта, `readConfig`, `createBot`, диспетчер grammY, запуск агента и PATH shim.

| Шаг | Проверенное поведение |
| --- | --- |
| Первый `/start`, AI ещё не подключён | Экран подключения; нет вызова модели и выбранной сессии |
| Инструкция Codex → `/settings` → «Подключения» → вход | Переходы по реально отрисованным кнопкам; синтетическая выдача device-кода и проверка статуса проходят через рабочий обработчик входа |
| `/start` после входа | Прежнее приветствие с вопросом об имени и занятии, без главного меню |
| Первый текст владельца | Отдельная беседа знакомства, верные каталог и нативный профиль, исходный текст передан один раз |
| `/start` во время первого хода | Знакомство остаётся активным; частичная заметка не открывает главное меню |
| Следующий ответ владельца | Возобновляется та же беседа знакомства |
| Естественное завершение | Частная сводка использует ту же сессию и read-only режим; допустимые факты сохраняются в `USER.md`/`MEMORY.md`, исходные правила и заметка сохраняются |
| После сохранения профиля | Появляется маркер завершения; итоговый ответ предшествует единственной карточке сервисов |
| Повторный `/start` | Открывается главное меню, карточка сервисов не дублируется |
| Первая обычная задача | Один ход app-server продолжает сохранённую сессию знакомства; ответ содержит обычный футер |

Точная последовательность нативных вызовов в тесте: device login → login
status → первый `exec` → возобновлённый `exec` → частная сводка `exec` →
обычный app-server turn. Проверены профиль, рабочий каталог, идентификаторы
возобновления и единственная передача каждого текста.

Раньше проверки экрана подключения и входа выполнялись отдельно, а основные
bootstrap-фикстуры заранее выбирали Codex. Исходные девять связанных файлов
давали **102/102 PASS** и не выявляли описанные ниже ситуации. Новый составной
сценарий закрывает разрыв между стартовой регистрацией, кнопками входа и
первым ходом.

## 1. Частично записанный профиль преждевременно завершал знакомство

**Коммит:** [6805f99a](https://github.com/SergeyKoleda/Jarvis/commit/6805f99a9ff57d50c665b62b48dc526000994a57).

Модель может изменить `SOUL.md` до завершения ответа. Если затем приходит
ошибка или владелец нажимает `/stop`, запись попытки знакомства остаётся
незавершённой. Но [проверка готовности workspace](../../.msb/bot/src/agent/bootstrap-workspace.mjs)
раньше принимала изменённый `SOUL.md` за готовый профиль **до** учёта
активной попытки. `/start` показывал «Готов. Пиши задачу», а следующий
текст уходил в обычный ход без частной сводки и маркера завершения.

Тот же порядок проверок давал неверное главное меню во время ожидания
частной сводки или после сбоя записи файлов. В этих случаях у runner уже
был `finish: 'profile'`, и следующий запрос всё ещё повторял финализацию;
отображаемая готовность расходилась с состоянием исполнения.

Теперь прежний маркер завершения по-прежнему имеет приоритет. Если маркера
нет, а вызывающий модуль уже сопоставил активную попытку с теми же
чатом/темой, workspace и нативным профилем, частично записанные файлы
не делают её готовой. Успешный `checkpoint` по-прежнему замечает изменение
`SOUL.md` и запускает существующие сводку, публикацию и передачу сессии.

Файлы владельца сохраняются. Для продолжения после ошибки или `/stop`
нужно следующее сообщение владельца; `/start` только показывает существующее
приветствие. Исходный прерванный запрос автоматически не повторяется.
Предварительно существующий профиль вне совпавшей попытки, другой нативный
профиль, маркер завершения и явный `/clear` сохраняют прежние правила.

Четыре проверки настоящего Telegram ingress дали **0/4 → 4/4**:

- `/stop` после записи изменённого `SOUL.md`;
- ошибка модели после той же записи;
- `/start` при незавершённой частной сводке;
- `/start` после ошибки публикации `MEMORY.md`.

Две проверки прерывания также подтверждают, что следующий новый текст
проходит через знакомство и сводку, исходный запрос не повторяется,
частичные файлы не перезаписываются, а карточка сервисов появляется один раз.
Связанные девять файлов после исправления: **105/105 PASS**.

## 2. Отсутствующая рабочая папка блокировала первый текст

**Коммит:** [6be2d013](https://github.com/SergeyKoleda/Jarvis/commit/6be2d01346e3675e7c32871fad753718329f5343).

Условие: Codex выбран, обычной сессии и выбранного проекта нет, настроенная
базовая рабочая папка отсутствует. `/start` корректно приветствовал владельца,
но первый текст завершался `ENOENT` при `realpath`; модель не запускалась.
В [codex-bootstrap.mjs](../../.msb/bot/src/agent/codex-bootstrap.mjs) создание
папки уже было предусмотрено, однако выполнялось после захвата канонического
`cwd` и поэтому оставалось недостижимым.

Теперь путь сначала проходит существующий resolver проекта. Только для новой
попытки в базовом workspace без выбранного проекта папка создаётся до
`realpath`, после проверки отмены. Выбранный отсутствующий проект не создаётся
и не заменяется базовой папкой. Для уже начатой попытки старые проверки пути
сохранены; повторная проверка профиля, проекта, эпохи и `cwd` перед запуском
модели остаётся на месте.

Регрессия первого ввода дала **0/1 → 1/1**: один запуск знакомства, исходный
текст один раз, правильные каталог/профиль, отдельный ID знакомства,
неизменённый нативный конфиг. Отрицательная проверка перемещает рабочую папку
после первого успешного хода: следующий ввод сохраняет прежнюю ошибку,
не создаёт замену папке, не меняет запись попытки и не вызывает модель снова.
Обе проверки — **2/2 PASS**.

Это условный сбой прямого запуска или восстановления с отсутствующей папкой.
[Штатный установщик](../../bootstrap/install.sh) заранее создаёт workspace
и копирует seed; утверждение о поломке каждого обычного первого запуска
не делается. Исправление не копирует seed, не меняет авторизацию и не
перезаписывает файлы владельца.

## Пределы проверки

Настоящие подготовка overlay, восстановление проекта и обработчики проверены
с подставным Telegram API и минимальным исполняемым Codex peer. Верхние
`index.js`/`main()` просмотрены по исходнику; polling, планировщики,
установщик, настоящий аккаунт, модель и живой Telegram в тесте не запускаются.
Это не живая приёмка и не доказательство совместимости всех версий CLI.

Отложены два точных имени из
[first-start-excluded.json](2026-11-20-first-start-excluded.json): смешанный
тест знакомства с выбором Claude/OpenClaw и смешанная матрица активации
сессии с переходом на `engine: 'oc'`. Их общие части также не выполнялись.
Node фильтрует эти имена до выполнения, поэтому они не отражены в `skipped`.
Инертная чужая запись в проверке целостности Codex ledger не активирует
OpenClaw. Работы по его сценариям остаются отложенными.
