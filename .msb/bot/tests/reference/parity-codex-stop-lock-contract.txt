Codex stop during a contended sleep marker (RED → GREEN)

User-facing contract: the already supported /stop, /stop@bot and reply «стоп»
interrupt an active Codex turn even while the bot is paused; stopping must not
wake the bot or change its provider/session. This is the current Codex contract,
not a claim that the old kernel had Codex. The old blob
73aa9e7e850bad7ac1ea8a8091d086ecbfd47a11:118208-118263 interrupts the active
turn on /stop; 109826-109879 gates inputs while asleep. Inspect with
  git show 73aa9e7e850bad7ac1ea8a8091d086ecbfd47a11 | sed -n '118208,118263p;109826,109879p'

RED: when a synthetic marker lock is held, both core-only and overlay+core
wait before dispatching all three stop variants. Releasing the lock lets the
stop reach the fake active turn; its marker and captured session remain intact.
The original diagnostic asserting the defect is preserved in commit 8c60034;
it is not a release test. The new shared stop predicate and provider-scoped
admission bypass the marker transaction for an already permitted Codex stop.
Overlay only takes this route for the owner, a present marker and selected Codex;
a reply owned by an overlay form retains that form's existing priority. Awake
slash commands retain normal form cancellation; paused slash behavior remains
unchanged. The gate still checks owner before model/stop dispatch.

GREEN: the executable regression asserts all six stop paths interrupt before
the held lock is released. It also checks owner scope, stop lookalikes, awake
and paused overlay forms, a core form and an unreadable marker. A form-owned
reply can still wait for the marker: its prior routing has not been changed.
The separate issue of /stop for an already-running direct interval remains.
Temporary profile, fake Telegram/turn and mocked engine status only; no real
model, credentials, network, JAR1 or unrelated engine behavior is involved.
Run from iia root:
  node .msb/bot/tests/reference/probe-codex-stop-lock.mjs

Validation: on local Node 26 and isolated Linux arm64 Node 22.23.2, 64
related top-level tests passed (their child wrappers additionally assert 16
stop-lock and 11 provider/pause synthetic cases), 13 sleep-flow cases with
engine status mocked, and 10 selected stop/form cases. The original selected
menu test timed out on both platforms; an independent archive of 8c60034
confirmed its expectation predated the already-requested new-message delivery.
Commit 0d21a6c updates that test only. The new fix was not tested on JAR1 or
with a real account. Marker reads and session data in these cases are synthetic;
the provider state and marker are not claimed atomic across processes.
