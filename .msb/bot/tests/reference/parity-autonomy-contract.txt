Interval persistence checkpoint.
Rz→ir (24883,24928–24949) records the result of one action; U4 (4393–4408)
updates that ID through oA's file transaction and keeps other IDs from the latest
file. It does not save a whole action list captured before a long runner call.

New baseline b5a781d store/scheduler lost concurrent addTask while the runner was
pending, collided on same-PID temp writes and could resurrect a removed task.
Five deterministic regressions RED; the fix reuses shared/file-lock.mjs, reloads
before write and conditionally commits only one unchanged task's execution fields.
A failed later task cannot roll back an already completed task checkpoint.
Independent processes add tasks to the same JSON in a separate regression.
All HOME/data/runner/notifications in these tests are synthetic; no real API/CLI.

Scope: no new timer controls, rights, UI, task types or change to nextAt semantics.
Old interval uses each run's start (Rz24757–24759,ir24883,lwA36099–36122), not its
completion. The current tick-wide now issue for later tasks is a separate case.
Task JSON locking does not reserve execution across multiple scheduler processes
or external writers that bypass the store. A changed task's stale result is
intentionally discarded; no exactly-once or instant abort-on-edit is promised.

53fb3fc reproduces six defects at the old Telegram ingress with a
disposable HOME. The management fix uses sessionDir's mapped parent,
preserves unknown fields and only updates the selected ID under the
existing file lock. A damaged array/file is never replaced by a menu
write. The UI keeps the old wording and callbacks and escapes stored
markup. The session override, corrupt bytes and concurrent callbacks
are checked separately. The old ZF write follows an existing link.
The new lock and atomic replacement use its physical target and keep
the link. An exclusive temporary file in an owned directory cannot
overwrite another file through a pre-existing predictable temp link.
Two cases reproduced both write defects before this correction.

Dispatch is a separate step. 18259–18271 and 108800–108830 show the old
once guard, triggerMessage and lastRunAt/disable after delivery. The
conversation prompt at 24608/24644 and parser at 26729–26748 distinguish
new SCHEDULE_TASK one-shot actions from legacy timer management. A
new reminder must use the action path. An active legacy store or its
global migration must not be inferred from these synthetic menu tests.
